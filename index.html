Week 1 · Lesson 1

UI, UX and enterprise information systems

UI purpose UX impact Project launch Critical analysis

Relevant syllabus content

  • Describe the purpose of user interfaces and interactive media, and explain how they affect the user experience.
  • Explore how user interfaces have evolved in response to people’s needs and opportunities.
  • Investigate design principles and issues relevant to user interfaces and interactive media.

Key terminology

User interface (UI)
The visible and interactive parts of a digital product, including its screens, buttons, menus, forms, icons and navigation.
User experience (UX)
The complete experience a person has while using a product, including how clear, efficient, accessible and trustworthy it feels.
Interactive media
Digital content that responds to a user’s actions or choices.
Enterprise information system
A system that helps an organisation collect, store, process and communicate information.
Visual hierarchy
The arrangement of interface elements so users can recognise what is most important.
Affordance
A visual or physical clue that suggests how an element should be used.

Read and understand

A user interface is the part of a digital product that a person directly sees and controls. It includes buttons, menus, search tools, forms, labels, icons, colours and navigation. Effective interfaces make important actions visible and predictable, allowing users to understand what they can do without relying on lengthy instructions.

User experience describes the quality of the complete interaction. An interface may look modern but still create poor UX if users cannot find information, understand feedback, recover from mistakes or complete a task efficiently. Strong UX considers clarity, accessibility, consistency, trust and the needs of the intended users.

During this unit, you will create an enterprise information system using Google Sheets and AppSheet. The app must help users add, search, edit and view structured data. Your interface decisions should not be based only on appearance; every screen and control must help the user complete a meaningful task accurately and confidently.

Inputs, processes, storage, transmission and outputs

Systems thinkingData flow

Relevant syllabus content

  • Explore inputs, storage, transmission, processes and outputs in UIs or interactive media.

Key terminology

Input
Data entered into or collected by a system.
Process
An action performed on data.
Storage
The place where data is kept.
Transmission
The movement of data between devices or services.
Output
Information produced or displayed by a system.

Read and understand

Information systems can be understood by examining how data moves through them. Users provide inputs through forms, selections, images or sensors. The system then checks, changes, calculates or organises that data.

Processed data is usually stored so it can be accessed again later. In this unit, Google Sheets acts as the structured data store while AppSheet provides the interface. Data is transmitted between the user, AppSheet and Google services.

Outputs are the results shown to users, such as a confirmation message, filtered list, chart or dashboard. A well-designed system makes each stage clear and prevents users from wondering whether their information has been saved.

Defining the problem, users and use cases

Problem definitionUser rolesUse cases

Relevant syllabus content

  • Define a real-world problem or need that can be solved by UIs or interactive media, including breaking it down into manageable parts and describing the users of the solution.
  • Specify the functional requirements of a UI or interactive media product, including stating the purpose of a solution and describing use cases.

Key terminology

Problem statement
A clear explanation of the issue a solution will address.
User role
A type of user with particular responsibilities or permissions.
Use case
A description of how a user completes a goal using the system.
User need
A task, difficulty or requirement experienced by a user.

Read and understand

Strong digital projects begin with a clearly defined problem. The problem should describe who is affected, what difficulty they currently experience and why the difficulty matters. Beginning with a solution idea alone can lead to features that do not address a real need.

Different users may interact with the same system in different ways. For example, a student may add data while a teacher reviews summaries. Identifying user roles helps designers decide what each person should be able to view, add, edit or delete.

A use case connects a user to a goal. It explains what the user wants to do and why. These use cases later become a guide for interface design, database structure and testing.

A strong project starts with a specific problem, not simply an app idea. Your problem statement should identify the users, their need and the improvement the proposed system will create.

Functional and non-functional requirements

RequirementsSuccess criteria

Relevant syllabus content

  • Specify the functional requirements of a UI or interactive media product.
  • Specify the non-functional requirements of a UI or interactive media solution.

Key terminology

Functional requirement
A statement describing what the system must do.
Non-functional requirement
A statement describing how well the system should operate.
Success criteria
Measurable conditions used to judge whether the project is successful.
Requirement
A feature, behaviour or quality the solution must provide.

Read and understand

Functional requirements describe the actions and features a system must provide. Examples include adding a record, calculating a total, filtering by status or displaying an image. They should be written clearly enough to test later.

Non-functional requirements describe qualities such as usability, accessibility, performance, security and reliability. Statements such as 'easy to use' are too vague unless they are made measurable.

Requirements guide development and help groups avoid adding unnecessary features. They also provide a fair basis for evaluation because the final product can be tested against the standards decided at the beginning.

Guided learning

Turn vague ideas into measurable requirements. Replace “easy to use” with a testable statement, such as “A first-time user can add a record in under two minutes without help.”

Requirements drafting

Complete the functional and non-functional requirement activity. Include requirements for data, navigation, accessibility, privacy and performance.

Peer quality check

Ask a partner to highlight requirements that are unclear, impossible to test or not connected to the project problem. Revise at least two.

Exit ticket

Functional requirements describe what the system must do. Non-functional requirements describe how well it should operate or the qualities it should have.

Functional examples

Add a booking; edit an item; search records; calculate an order total; display a dashboard.

Non-functional examples

Week 2 · Lesson 5

Test cases: inputs and expected outputs

TestingValidation

Relevant syllabus content

  • Develop test cases of inputs and expected outputs.
  • Validate data is correct and investigate the impact of invalid data.

Key terminology

Test case
A planned test with an input, action and expected result.
Normal data
Typical valid data.
Boundary data
Data at the edge of an accepted range.
Invalid data
Data that should be rejected.
Expected output
The result the system should produce.

Read and understand

Testing checks whether a system behaves as expected. A good test case states exactly what will be entered or selected and what result should occur. Another person should be able to repeat the same test.

Normal tests check common use, while boundary tests check the limits of accepted values. Invalid tests check whether the system prevents incorrect, missing or inappropriate data from being stored.

Testing should begin during planning rather than after the app is finished. Early test cases help designers create validation rules and identify how the system should respond when something goes wrong.

Exit ticket

A test case states the feature being tested, the input or action, the expected result and the actual result. Good testing includes normal, boundary and invalid data.

Privacy
The appropriate collection, use and protection of personal information.

Read and understand

Digital systems can affect individuals and communities, so designers must consider more than technical function. They need to think about privacy, consent, fairness, copyright, access and the possible consequences of collecting data.

Inclusive communication and accessibility

AccessibilityDiverse audiencesCommunication

Relevant syllabus content

  • Investigate and evaluate the influence of communication methods on an audience, including the perspectives of diverse groups that may include Aboriginal and Torres Strait Islander Peoples, culturally and linguistically diverse people, people of different ages and gender, and people with disability.
  • Design and implement a UI, UX or interactive media product allowing for accessibility and usability.

Key terminology

Accessibility
Designing so people with different abilities and needs can use a product.
Inclusive design
Design that considers a wide range of users from the beginning.
Audience
The people for whom information is created.
Communication method
The way information is presented, such as text, icons, audio or images.

Read and understand

Accessible design helps more people use a product successfully. Clear labels, readable text, logical navigation and large touch targets can assist users with different levels of vision, language, experience or physical ability.

Information should not be communicated using colour alone because some users may not perceive colour differences. Designers can add labels, icons, shapes or text so that meaning remains clear.

Inclusive communication also requires respectful representation. Designers should avoid stereotypes, recognise diversity within communities and seek permission before using cultural images, stories or knowledge.

Do now: accessibility barrier

Guided learning

Review readable, perceivable, operable and respectful design. Notice that accessibility is not an extra feature added at the end; it shapes labels, layout, colour, navigation and testing.

Redesign challenge

Choose a confusing form or screen. Describe how you would improve labels, field order, instructions, error messages and colour use.

Audience review

Explain how your app communicates effectively with two different audience groups.

Exit ticket

Communication choices influence whether an audience can understand, trust and use a product. Designers should consider people of different ages, genders, cultures, language backgrounds and abilities.

Readable

Clear labels, plain language, sufficient text size and useful spacing.

Perceivable

Do not rely on colour alone. Add text, icons, patterns or labels.

Operable

Logical navigation, large touch targets and predictable controls.

Respectful

Avoid stereotypes and seek feedback from the people represented.

When designing for Aboriginal and Torres Strait Islander Peoples, avoid treating cultures as one single group. Use respectful language, recognise diversity between communities and do not use cultural images, stories or knowledge without permission.

Compression, file formats and media choices

LossyLosslessPerformance

Relevant syllabus content

  • Explain simple compression of data and types of compression, including lossy and lossless compression.

Key terminology

Compression
Reducing the size of a digital file.
Lossy compression
Compression that permanently removes some information.
Lossless compression
Compression that preserves all original information.
File format
The structure used to store a type of digital file.

Read and understand

Compression reduces the amount of storage and transmission time needed for digital files. Smaller files usually load faster, which can improve the user experience of an app or website.

Lossless compression keeps all original information and is useful when accuracy matters. Lossy compression removes some information to create a smaller file and is commonly used for photographs, audio and video.

Media choices should match the purpose of the product. A clear logo may require a PNG file, while a photograph may be more efficient as a JPEG. Large images should be resized before being added to an AppSheet database.

Exit ticket

Compression reduces file size. Smaller files usually load and transmit faster, but the chosen method affects quality.

Lossless compression

No information is permanently removed. The original can be reconstructed. Useful when accuracy matters.

Lossy compression

Some information is permanently removed to create a smaller file. Useful for photographs, audio or video when a small quality reduction is acceptable.

Structured data: tables, entities, attributes and keys

Database designEntitiesKeys

Relevant syllabus content

  • Represent, store and display data to facilitate computation, including selecting appropriate data types, understanding data type limitations and structuring data systematically.
  • Model entities, events and their attributes using structured data.

Key terminology

Entity
A person, object, place, event or concept stored in a database.
Attribute
A property used to describe an entity.
Record
One complete set of data about an entity.
Primary key
A unique value that identifies each record.
Relationship
A connection between tables.

Read and understand

Databases organise information into tables. Each table normally represents one entity, such as a user, item, booking or task. The columns describe attributes and the rows store individual records.

A primary key gives every record a unique identity. Keys should be stable and should not rely on names because names can be duplicated or changed.

Connected tables reduce repeated data and make the system easier to manage. A reference field can link one table to another, such as an Order record linking to the User who created it.

Relevant syllabus content

Key terminology

Data type
The kind of value stored in a field.
Validation
A rule that checks whether data is acceptable.
Enum
A field that restricts users to a set of choices.
Reference field

Data quality

Read and understand

Choosing the correct data type allows a system to treat information properly. Numbers can be calculated, dates can be compared, images can be displayed and yes/no fields can provide clear choices.

Validation reduces mistakes before they enter the database. Required fields, ranges, dropdowns and format checks can prevent incomplete or inconsistent records.

Poor-quality data can affect filters, formulas, charts and decisions. Designers must test for missing values, duplicates, incorrect categories and values stored in the wrong format.

Least privilege
Giving users only the access needed for their role.

Read and understand

Security involves protecting data from unauthorised access, accidental sharing, alteration or deletion. It also includes decisions about who should be able to perform different actions.

Privacy and security are connected but not identical. Privacy focuses on appropriate collection and use of information, while security focuses on protecting that information.

Student projects should use fictional or mock data wherever possible. Sharing settings should be reviewed carefully, and source spreadsheets should not be made public without approval.

Threat scenario

Exit ticket

Security is not simply “adding a password”. It involves minimising data, controlling access, selecting appropriate sharing settings and explaining how data moves and is protected.

Key terminology

Data visualisation
Representing data using charts, graphs or other visuals.
Trend
A general pattern in data.
Outlier
A value that is noticeably different from others.
Dashboard
A collection of related summaries and visualisations.
Prediction
A judgement about what may happen based on evidence.

Read and understand

Visualisations help users understand large amounts of data quickly. A chart should answer a useful question rather than simply decorate the app.

Different charts suit different purposes. Bar charts compare categories, line charts show change over time and dashboards combine related summaries for decision-making.

Designers should identify trends and outliers carefully. Predictions should be based on evidence, but they should also acknowledge limitations such as small datasets or missing information.

Use the evidence from your visualisation to make one prediction or decision. Explain the limitation of that prediction.

Exit ticket

Visualisations should help users answer a question. A chart is useful when it reveals a pattern, comparison, trend or unusual value.

User testing, peer feedback and iteration

UsabilityEfficiencyIteration

Relevant syllabus content

  • Evaluate their own project and that of their peers using the previously developed functional and non-functional requirements.
  • Test and evaluate a UI to improve usability and overall efficiency.

Key terminology

Usability testing
Testing how easily users can complete tasks.
Efficiency
The time and effort needed to complete a task.
Iteration
Repeating design, testing and improvement.
Peer feedback
Comments and observations provided by another student.
Retesting
Testing again after a change has been made.

Read and understand

User testing reveals problems that the creator may no longer notice. First-time users often identify unclear labels, unexpected navigation and unnecessary steps.

Testing should measure observable outcomes such as task completion, errors, time, requests for help and user confidence. Feedback is most useful when it is connected to a specific requirement.

Iteration means making a change based on evidence and then testing again. Strong project documentation shows the original problem, the change made and the result of retesting.

Key terminology

Evaluation
A judgement about how well a solution meets its goals.
Reflection
Consideration of learning, decisions and contributions.
Evidence
Information used to support a judgement.
Limitation
A weakness or restriction in a solution.
Recommendation
A proposed future improvement.

Read and understand

Evaluation compares the completed product with its original functional and non-functional requirements. It should make clear judgements rather than only describe what the app contains.

Claims should be supported with evidence such as test results, user feedback, screenshots, data summaries and examples of improvements. A balanced evaluation identifies both strengths and limitations.

Reflection also considers the development process and group collaboration. Students should explain individual contributions, challenges, changes in thinking and improvements they would make in a future version.
